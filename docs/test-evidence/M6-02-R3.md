## Findings and independently reviewed expectations

Eight new success/rejection cases distinguish an invocation's completion from
earlier version protection:

- Session capture: after version 1 is confirmed, a second Save awaits a gated
  capture while the prior receipt still yields `Saved locally`. No checkpoint
  or source request is dispatched before capture succeeds. Rejection completes
  that invocation without another receipt; identity/content/selection survive,
  and explicit retry works. This uses a fake editor, not native capture/IME.
- Cadence ordering: independently supplied literal `a`/`b` snapshots and hashes
  establish source requests **21, 22, 22**. Save awaits the older request, then
  the drained latest request, then its own fresh duplicate flush. Baselines
  advance only from the preceding verified receipts. Version 21 does not mark
  version 22 saved. Even after version 22 is confirmed, the duplicate gate keeps
  this invocation pending. Rolling work is already complete. Both duplicate
  success/rejection settle, empty the pending queue and allow explicit retry.
  Separate older/latest rejection variants also settle; failed receipts do not
  advance the baseline and the invocation still dispatches its fresh flush.
- Real-editor JSDOM: a completed edit/Save supplies the first receipt; the next
  unchanged Save defers only the injected source port. Its DOM still displays
  the earlier `Saved locally`, while Save and Home are disabled and editing
  remains enabled. Success/rejection restores both actions. Rejection displays
  `Save failed` with the earlier source bytes intact; a fresh retry succeeds.
  Literal independently authored BOM/CRLF, trailing spaces and retained note
  bytes, selection and one-step Undo/Redo survive without replacing the view.
  The port's byte buffer is a simulation, not a filesystem durability claim.

The existing `FlushSummary.saved`/`recovered` fields describe retained exact
version protection, not whether the latest duplicate verification succeeded.
After a typed duplicate I/O rejection, both can remain true while controller
status is `Save failed`; no new receipt was earned. Existing visible status
remains truthful. Source review confirms protected close awaits its own fresh
controller Save rather than using the cadence summary as release credit.
No summary, receipt, status, close or snapshot contract was changed.

Expected bytes were reviewed directly from literal external-style source and
explicit inserted `X`; expected hashes use independently known single-byte
hashes or Node SHA-256. They were not generated from product capture output.
Existing controller stale-ack/baseline tests and R2 snapshot controls pass in
the focused selection. These tests identify reachable waits and settled gates;
they neither recreate a native deadlock nor explain the historical failure.
